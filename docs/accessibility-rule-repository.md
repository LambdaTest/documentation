# Accessibility Rule Repository

Every accessibility rule TestMu AI evaluates across web, Android, and iOS, mapped to its WCAG success criterion with concise remediation guidance. Switch platforms with the tabs below.

<Tabs>

<TabItem value="web" label="Web (37)">

Web rules map directly to WCAG success criteria.

| Rule | WCAG | What it checks | How to fix |
| --- | --- | --- | --- |
| **Non-text Content (1.1.1)** | [1.1.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html) | Meaningful non-text content exposes an accessible text alternative that explains its purpose or information. | • add accurate alt text for meaningful content<br />• mark decorative content as decorative so it is ignored correctly<br />• ensure icon-only controls expose an accessible name through the appropriate attribute or label |
| **Info and Relationships (1.3.1)** | [1.3.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/info-and-relationships.html) | Headings, lists, tables, form groups, and landmark regions use correct semantic HTML rather than relying on visual appearance alone. | • use native semantic elements for headings, lists, tables, and form groups<br />• add ARIA landmarks only when native elements are not available<br />• verify heading levels follow a logical nesting order without skipping levels<br />• test with a screen reader to confirm the announced structure matches the visual layout |
| **Orientation (1.3.4)** | [1.3.4 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/orientation.html) | CSS or viewport meta configurations that lock the page to a single orientation, preventing users from rotating their device. | • support both portrait and landscape orientations through responsive design<br />• remove JavaScript orientation locks unless the content genuinely requires a specific orientation (e.g., a piano keyboard app)<br />• test the layout in both orientations on real devices<br />• if a specific orientation is essential, clearly document why |
| **Use of Color (1.4.1)** | [1.4.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) | Instances where meaning is communicated exclusively through color without a secondary visual indicator such as text, icons, patterns, or underlines. | • pair color with a text label, icon, pattern, or border change<br />• underline links or add a visible icon to distinguish them from surrounding text<br />• use patterns, hatching, or data labels in charts alongside color<br />• test the interface with a color-blindness simulator to confirm the secondary cue is visible |
| **Reflow (1.4.10)** | [1.4.10 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) | Content that causes horizontal scrolling at 320px viewport width (equivalent to 400% zoom on a 1280px desktop display). | • use responsive CSS (relative units, `max-width`, flexbox/grid) to allow single-column reflow<br />• wrap wide tables in a scrollable container so the rest of the page still reflows<br />• set images to `max-width: 100%` so they scale within their container<br />• test at 320px viewport width (or 400% zoom) and fix any horizontal overflow |
| **Non-text Contrast (1.4.11)** | [1.4.11 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) | The contrast of interactive component boundaries (input borders, button outlines, focus indicators) and meaningful graphical objects (icons, chart segments) against their backgrounds. | • ensure input and button borders meet the 3:1 ratio against adjacent background colors<br />• verify icon contrast against both light and dark backgrounds<br />• add borders or patterns to chart segments alongside color fills<br />• test all interactive states (default, hover, focus, active) for contrast compliance |
| **Text Spacing (1.4.12)** | [1.4.12 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/text-spacing.html) | Content is clipped, truncated, or overlapping when text spacing is increased to WCAG-specified thresholds: line height 1.5x font size, paragraph spacing 2x font size, letter spacing 0.12x font size, word spacing 0.16x font size. | • avoid fixed heights on text containers; use `min-height` or auto-height<br />• do not use `overflow: hidden` on elements that contain user-facing text<br />• test with a text-spacing bookmarklet that applies the WCAG thresholds<br />• ensure layouts flex and reflow when text occupies more space |
| **Audio Control (1.4.2)** | [1.4.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/audio-control.html) | Pages where audio or video with sound starts automatically and runs beyond three seconds without an accessible pause or volume control. | • never autoplay audio; if autoplay is required, start muted and let the user opt in<br />• provide a visible, keyboard-accessible pause or mute control near the top of the page<br />• ensure the control is the first or one of the first focusable elements so screen-reader users reach it quickly |
| **Contrast (Minimum) (1.4.3)** | [1.4.3 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) | Text and important UI elements meet the minimum contrast requirements needed for readable, usable interfaces. | • increase the contrast between foreground and background colors<br />• verify contrast after hover, focus, and active-state styling is applied<br />• avoid relying on color tokens that look correct in one theme but fail in another |
| **Keyboard (2.1.1)** | [2.1.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) | Interactive elements (links, buttons, form controls, and custom widgets) are reachable and operable using keyboard alone: Tab, Shift+Tab, Enter, Space, and arrow keys as appropriate. | • use native interactive elements (`<button>`, `<a>`, `<select>`) whenever possible<br />• add `tabindex="0"` and keyboard event listeners to custom interactive widgets<br />• provide keyboard-equivalent actions for drag-and-drop, swipe, and hover interactions<br />• test the entire flow using only the keyboard (Tab, Enter, Space, Escape, arrows) |
| **No Keyboard Trap (2.1.2)** | [2.1.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/no-keyboard-trap.html) | For components that capture keyboard focus and prevent the user from tabbing or escaping out using standard keys. | • ensure Escape closes modals and returns focus to the trigger element<br />• implement focus trapping in modals correctly: trap while open, release on close<br />• allow Tab to exit custom editors (provide a documented key combination or a skip link)<br />• test by tabbing into and then out of every interactive region on the page |
| **Character Key Shortcuts (2.1.4)** | [2.1.4 (A)](https://www.w3.org/WAI/WCAG22/Understanding/character-key-shortcuts.html) | Keyboard shortcuts bound to single character keys that are active globally on the page rather than scoped to a focused component. | • require a modifier key (Ctrl, Alt, Shift) for global shortcuts<br />• scope single-character shortcuts so they only work when the relevant component is focused<br />• provide a settings UI to disable or remap character shortcuts<br />• if modifier keys are not feasible, ensure the shortcut deactivates when a text input has focus |
| **Timing Adjustable (2.2.1)** | [2.2.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html) | Session timeouts, auto-redirects, and auto-updating content that impose a fixed time limit without user control. | • provide a warning at least 20 seconds before a timeout and allow the user to extend it<br />• allow users to disable or increase time limits in account or session settings<br />• add pause, stop, and resume controls to auto-advancing content<br />• for real-time exceptions (auctions, live events), clearly document the constraint |
| **Pause, Stop, Hide (2.2.2)** | [2.2.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html) | Animations, auto-scrolling regions, and auto-updating feeds that run for more than five seconds without user controls. | • add visible pause, stop, or hide controls for any auto-moving content<br />• respect the `prefers-reduced-motion` media query to minimize or remove animation<br />• for live feeds, allow the user to opt in to updates rather than pushing them automatically<br />• ensure controls are keyboard accessible and announced by screen readers |
| **Three Flashes or Below Threshold (2.3.1)** | [2.3.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html) | Content that produces rapid flashing (more than three flashes per second) in a large enough area to exceed safety thresholds. | • limit flashing to three or fewer per second in any region of the page<br />• use the Photosensitive Epilepsy Analysis Tool (PEAT) to test video and animation content<br />• provide a warning before content that contains known flashing and allow the user to skip it<br />• respect `prefers-reduced-motion` to suppress flashing animations |
| **Bypass Blocks (2.4.1)** | [2.4.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/bypass-blocks.html) | Verifies the presence of skip-navigation links, landmark regions, or heading structures that allow users to bypass repeated content and jump directly to the main content area. | • add a "Skip to main content" link as the first focusable element, visible on focus<br />• use `<main>` to wrap primary content and `<nav>` for navigation blocks<br />• ensure heading levels provide meaningful structure users can navigate by<br />• test by pressing Tab immediately after page load to confirm the skip link appears and works |
| **Focus Not Obscured (Minimum) (2.4.11)** | [2.4.11 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) | Focused elements are not fully concealed behind sticky navigation bars, cookie banners, chat widgets, or other fixed-position elements. | • add scroll padding (e.g., `scroll-padding-top`) to account for sticky header height<br />• ensure cookie banners and chat widgets do not overlap focusable page content<br />• implement `scrollIntoView` with appropriate offsets when managing focus programmatically<br />• test by tabbing through the entire page and confirming every focused element is at least partially visible |
| **Page Titled (2.4.2)** | [2.4.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/page-titled.html) | Each page has a non-empty `<title>` element and that the title text meaningfully describes the page content. | • write titles in the format "Page Purpose - Site Name" (e.g., "Order History - Acme Store")<br />• update `document.title` on route changes in single-page applications<br />• include key differentiators when pages are similar (e.g., "Edit Profile" vs. "View Profile")<br />• keep titles concise but specific enough to identify the page without seeing it |
| **Focus Order (2.4.3)** | [2.4.3 (A)](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html) | The tab order of interactive elements follows a logical reading sequence and does not jump unexpectedly between unrelated sections. | • rely on DOM source order rather than positive `tabindex` values<br />• ensure CSS visual reordering matches the underlying DOM sequence<br />• move focus into modals, dialogs, and drawers when they open, and return it when they close<br />• test with keyboard-only navigation to confirm the sequence feels natural |
| **Link Purpose in Context (2.4.4)** | [2.4.4 (A)](https://www.w3.org/WAI/WCAG22/Understanding/link-purpose-in-context.html) | Links whose text is generic (e.g., "click here", "read more", "learn more") without surrounding context that clarifies the destination or action. | • write link text that describes the destination or action (e.g., "View order #1234" instead of "Click here")<br />• use `aria-label` or `aria-labelledby` to provide context when the visible text must remain short<br />• add `aria-label` to icon-only links that describes the action<br />• when multiple links share text, add visually hidden context (e.g., "Read more about pricing") |
| **Focus Visible (2.4.7)** | [2.4.7 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html) | Users can see where keyboard focus currently is as they move through interactive elements. | • keep the default focus indicator or replace it with an equally visible custom style<br />• test focus styling on links, buttons, form fields, menus, and dialogs<br />• verify focus visibility in light and dark themes |
| **Pointer Gestures (2.5.1)** | [2.5.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/pointer-gestures.html) | Interactions that require multi-touch gestures (pinch, two-finger swipe) or precise path-based gestures (drawing a shape, swiping in a specific direction) without a single-click or single-tap alternative. | • add button controls for zoom, pan, and delete alongside gesture support<br />• provide single-tap or single-click alternatives for every multi-point gesture<br />• for path-based input, offer an alternative method (e.g., typed input, button sequences)<br />• test with a single mouse click/tap only to confirm all features remain accessible |
| **Pointer Cancellation (2.5.2)** | [2.5.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html) | Interactive elements do not fire irreversible actions on `mousedown` or `touchstart` alone, allowing users to abort by moving the pointer away before releasing. | • use `click` events rather than `mousedown` or `touchstart` for actions<br />• if down-event activation is needed, provide an undo or confirmation step<br />• implement drag cancellation by allowing users to drop outside the target zone<br />• test by pressing down on a button, dragging away, and releasing to confirm no action occurs |
| **Label in Name (2.5.3)** | [2.5.3 (A)](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html) | Compares the visible label text with the computed accessible name and flags mismatches where the visible text is not included in the accessible name. | • ensure the accessible name starts with or contains the visible label text<br />• prefer visible `<label>` elements over `aria-label` when visible text is available<br />• when `aria-label` is needed, include the visible text within it (e.g., `aria-label="Submit order form"` for a button labeled "Submit")<br />• test with voice-input software to confirm controls can be activated by speaking their visible label |
| **Motion Actuation (2.5.4)** | [2.5.4 (A)](https://www.w3.org/WAI/WCAG22/Understanding/motion-actuation.html) | Interactions driven by device sensors (accelerometer, gyroscope, camera) that do not offer an alternative button or control and cannot be disabled. | • provide an on-screen button or control for every motion-triggered action<br />• allow users to disable motion-based activation in settings<br />• if motion is essential to the functionality (e.g., a step counter), document the exception<br />• test with the device in a fixed position to confirm all functionality is reachable through UI controls |
| **Dragging Movements (2.5.7)** | [2.5.7 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) | Drag-and-drop interactions, slider controls, and reorderable lists that do not offer an alternative single-click or keyboard-based method. | • add move-up/move-down buttons or a "Move to" menu for reorderable lists<br />• support click-on-source then click-on-destination as an alternative to drag-and-drop<br />• ensure sliders can be adjusted with arrow keys, or provide a text input alternative<br />• always include a file browse button alongside drag-and-drop upload zones |
| **Target Size (Minimum) (2.5.8)** | [2.5.8 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) | Measures the rendered size of interactive elements (buttons, links, form controls) and flags those smaller than 24x24 CSS pixels that do not meet any exception criteria. | • ensure clickable areas are at least 24x24 CSS pixels (44x44 is recommended for touch interfaces)<br />• add padding or transparent borders to increase the hit area without changing the visual size<br />• use `min-width` and `min-height` on interactive elements<br />• increase spacing between adjacent small targets so users can tap accurately |
| **On Focus (3.2.1)** | [3.2.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/on-focus.html) | Elements that initiate a context change (navigation, submit, new window) when they receive keyboard focus rather than when they are explicitly activated. | • trigger context changes only on explicit activation (click, Enter, Space)<br />• for select menus that act as navigation, add a separate "Go" button<br />• never attach `onfocus` handlers that cause navigation, submission, or window changes<br />• test by tabbing through all interactive elements without pressing Enter |
| **On Input (3.2.2)** | [3.2.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/on-input.html) | Form controls that trigger navigation, submission, or DOM restructuring on value change without prior notice to the user. | • separate the selection action from the submission action (add a "Submit" or "Apply" button)<br />• if auto-submission is intentional, inform the user in advance (e.g., "Selecting a value will update the page")<br />• use ARIA live regions to announce dynamic content changes without a full context switch<br />• test all form controls by changing values and confirming no unexpected navigation occurs |
| **Consistent Help (3.2.6)** | [3.2.6 (A)](https://www.w3.org/WAI/WCAG22/Understanding/consistent-help.html) | Help-related UI elements maintain consistent placement and ordering across pages within the same site. | • place help mechanisms in the same relative position across all pages (e.g., always last in the footer)<br />• use a shared layout component to ensure consistent ordering automatically<br />• if multiple help options exist, keep their order fixed (e.g., FAQ, then Chat, then Email)<br />• audit help element placement across page templates to confirm consistency |
| **Error Identification (3.3.1)** | [3.3.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html) | Form validation errors are communicated through visible text messages associated with the relevant field, not only through color or icon changes. | • display a text error message adjacent to or within the erroneous field<br />• associate the error message with the field using `aria-describedby` or `aria-errormessage`<br />• set `aria-invalid="true"` on the field when an error is detected<br />• move focus to the first error or provide a summary with links to each erroneous field |
| **Labels or Instructions (3.3.2)** | [3.3.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html) | Form inputs have visible labels programmatically associated with the control, and that fields requiring specific formats include instructions. | • add a visible `<label>` element with a matching `for` attribute for every form control<br />• include format instructions or examples near the field (e.g., "Enter date as MM/DD/YYYY")<br />• use `<fieldset>` and `<legend>` for logically grouped fields<br />• never use placeholder as a substitute for a visible label |
| **Redundant Entry (3.3.7)** | [3.3.7 (A)](https://www.w3.org/WAI/WCAG22/Understanding/redundant-entry.html) | Multi-step flows where users are asked to re-enter information they have already provided in a previous step (e.g., name, address, email) without auto-fill or a selection option. | • auto-populate fields with information provided in earlier steps of the same process<br />• offer a "same as shipping" checkbox for billing address forms<br />• use session storage or form state management to carry data across steps<br />• if security requires re-entry (e.g., password confirmation), document the exception |
| **Accessible Authentication (Minimum) (3.3.8)** | [3.3.8 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html) | Login flows that rely solely on cognitive challenges (CAPTCHAs, image puzzles, memory-based knowledge questions) without offering an accessible alternative. | • allow password managers to auto-fill login fields (do not use `autocomplete="off"` on authentication fields)<br />• provide an accessible CAPTCHA alternative (audio CAPTCHA, email verification, or WebAuthn)<br />• support passwordless authentication (magic links, biometrics, passkeys)<br />• allow pasting into verification code fields for users who receive codes via email or authenticator apps |
| **Parsing (4.1.1)** | [4.1.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/parsing.html) | Validates HTML for duplicate IDs, malformed nesting, unclosed elements, and duplicate attributes that could confuse assistive technology parsers. | • run an HTML validator to catch structural issues<br />• ensure every `id` is unique within the page<br />• fix unclosed or misnested elements<br />• avoid nesting interactive elements inside each other |
| **Name, Role, Value (4.1.2)** | [4.1.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) | Interactive elements have an accessible name, an appropriate ARIA or native role, and that state changes (expanded, checked, selected, disabled) are communicated programmatically. | • use native HTML elements whenever possible (`<button>`, `<input>`, `<select>`)<br />• for custom widgets, add the appropriate ARIA role and maintain state attributes (`aria-expanded`, `aria-checked`, `aria-selected`)<br />• ensure every interactive element has an accessible name through visible text, `aria-label`, or `aria-labelledby`<br />• update ARIA states dynamically when the user interacts with the control |
| **Status Messages (4.1.3)** | [4.1.3 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) | Dynamic status messages use ARIA live regions (`role="status"`, `role="alert"`, `aria-live`) so screen readers announce them without moving focus away from the current task. | • use `role="status"` for non-urgent updates (result counts, save confirmations)<br />• use `role="alert"` for urgent messages (errors, warnings)<br />• ensure the live region exists in the DOM before the content is injected (add content to an existing container rather than injecting the container)<br />• avoid overusing alerts, since frequent announcements interrupt the user's workflow |

Android rules map to the closest WCAG criterion and cover TalkBack behavior.

| Rule | WCAG | What it checks | How to fix |
| --- | --- | --- | --- |
| **Button Element Capitalisation Check** | [3.1.6 (AAA)](https://www.w3.org/WAI/WCAG22/Understanding/pronunciation.html) | Reviews button labels — including clickable containers acting as buttons — for irregular capitalization: labels that begin with a lowercase letter, mid-word capitalization (e.g., "SubMit", "LogIn"), or an unnecessary capital after a hyphen in hyphenated labels (e.g., "Sign-In" instead of "Sign-in"). | • use sentence case (e.g., "Save changes") in the underlying string instead of all caps or inconsistent capitalization<br />• if a stylized all-caps look is desired visually, apply it through styling (`android:textAllCaps`) rather than in the source string, so the underlying accessible text remains normally cased<br />• keep hyphenated labels in sentence case too — "Sign-in", not "Sign-In" |
| **Duplicate Accessibility Label** | [4.1.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) | Groups of visible, interactive elements on the same screen that share an identical accessibility label — including duplicates across different widget types, such as a Button and a Switch both labeled the same way. All elements in a duplicate group are reported together so they can be reviewed as a set. | • ensure each interactive element has a unique accessibility label<br />• make labels contextual — include the item they act on: "Delete — Order #1234", "More options for John's playlist"<br />• review list and grid layouts first, since repeated item templates are the most common source of duplicates |
| **Dynamic Type Support** | [1.4.4 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) | Examines whether on-screen text is sized in `sp` (scale-independent pixels) — the only Android text unit that responds to the user's system-wide font-size preference. Text sized in fixed units (`dp`, `px`, `pt`, `in`, `mm`) renders at a fixed size no matter what the user configures. :::note The required device data is available on Android 11+ only; on older devices the rule passes silently rather than flagging an issue. ::: | • replace fixed-unit text sizes with scale-independent units so the accessibility font-scale takes effect — use `sp` for `android:textSize` instead of `dp` or `px`, and avoid setting a fixed text size on `TextView` / `Button` / `EditText`<br />• test at the system's largest font-size setting and confirm no text clips or truncates (see Non-Responsive Container Clips Text for the layout side of this) |
| **Emoji or Symbol Used in Accessibility Label** |  | Interactive elements whose accessible label is made up mostly or entirely of emoji, arrows, geometric shapes, or other special symbols instead of descriptive text. A label is flagged when half or more of its meaningful characters are emoji or symbols. Ordinary punctuation is acceptable; static (non-interactive) text is not checked. | • determine intent — check whether the emoji is functional (represents an action) or decorative<br />• replace functional emoji with a descriptive verb, e.g. change "❤️" to "Add to Favorites"<br />• hide decorative icons from the focus order instead of labeling them — set `android:importantForAccessibility="no"` |
| **Fixed Orientation Lock (Android)** | [1.3.4 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/orientation.html) | Activities with `android:screenOrientation` set to a fixed value (`portrait`, `landscape`, `sensorPortrait`, `sensorLandscape`) in the manifest, preventing device rotation. | • remove `android:screenOrientation` from the manifest (defaults to user-controlled rotation)<br />• only lock orientation when the content genuinely requires it (e.g., a camera viewfinder)<br />• test the app in both orientations to confirm layouts adapt correctly<br />• document any essential orientation requirement with a clear justification |
| **Images with Text** | [1.1.1 (A)](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html) | Examines images on the screen for meaningful text rendered inside the image itself — text that exists only as pixels, with no real text element carrying it. Detection is AI-based, analyzing the rendered screen rather than the view hierarchy alone. *(AI rule)* | • avoid embedding meaningful text inside images — use real text views (`TextView`) so TalkBack can read the content, or provide the text through `android:contentDescription`<br />• if the image is decorative, mark it as such (`android:importantForAccessibility="no"`) so screen readers skip it |
| **Inaccessible Text Focus** | [4.1.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) | `TextView` and other text-bearing elements that are not reachable through TalkBack navigation because they are marked as not important for accessibility or are hidden behind non-focusable containers. | • ensure text elements containing meaningful content have `importantForAccessibility="yes"`<br />• do not suppress descendant accessibility on containers that hold readable text<br />• remove decorative text from the accessibility tree with `importantForAccessibility="no"` (only when truly decorative)<br />• test by swiping through the screen with TalkBack and confirming all meaningful text is announced |
| **Insufficient Color Ratio** | [1.4.3 (AA)](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html) | Measures the contrast ratio between foreground text or icon colors and their background, flagging pairs that fall below the 4.5:1 ratio for normal text or 3:1 for large text. | • verify text contrast against backgrounds using a color contrast analyzer<br />• use Material Design color tokens that are pre-validated for contrast compliance<br />• ensure all text states (enabled, disabled, error, hint) meet minimum ratios<br />• test on multiple devices and brightness levels to catch theme-specific failures |
| **Insufficient Target Spacing** | [2.5.5 (AAA)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html) | Measures the gap between adjacent clickable or focusable elements and flags pairs that are too close together, increasing the risk of mis-taps. | • add at least 8dp of spacing between adjacent interactive elements<br />• use `android:layout_margin` or Compose `Modifier.padding` to create clear separation<br />• consider grouping related actions into an overflow menu to reduce density<br />• test on the smallest supported screen size to confirm spacing remains adequate |
| **Interactive Role Undefined (Android)** | [4.1.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) | Interactive elements (buttons, switches, checkboxes, sliders) that do not expose a recognized accessibility role to the Android accessibility framework. | • use native Android widgets (`Button`, `Switch`, `CheckBox`) whenever possible<br />• for custom views, override `getAccessibilityClassName()` to return the appropriate widget class name<br />• in Jetpack Compose, set `role = Role.Button` (or the appropriate role) inside `Modifier.semantics { }`<br />• test with TalkBack to confirm the announced role matches the element's behavior |
| **Invalid Range Values** | [4.1.2 (A)](https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html) | Examines range controls — sliders (`SeekBar`), progress bars, steppers — and reports controls whose range values are inconsistent: the current value falls outside the declared min/max range, or the min/max range itself is invalid. | • ensure min < max and the current value falls within [min, max] on the control (`SeekBar` / `Slider`)<br />• for custom range controls, expose the range to assistive technology via `AccessibilityNodeInfo.RangeInfo` |
