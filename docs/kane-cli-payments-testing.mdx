A payment flow can return a success page while the amount, the method, or the recorded status is wrong. These use cases check what the shopper sees against what the merchant side records: the receipt against the charge, the dashboard against the payment, and the order page against the webhook.

Every use case below was recorded against a demo payment app with test cards and test accounts, and comes with the `_test.md` file that produced the run. No real money moves in any of these runs, and you should point your own copies at a sandbox or test-mode environment.

## Run these recipes

Save any recipe below as a file ending in `_test.md`, change the `url` to your sandbox checkout, and replace the amounts, test cards, and IDs with values from your own test data. Then run it:

```bash
kane-cli testmd run tests/declined-card-recovery_test.md --agent
```

The first run authors and records each step, and later runs replay the recording. Keep card numbers and account passwords out of the file by passing them as variables, for example `{{test_card}}` with `--variables-file`. See [Variables & Context](/docs/kane-cli-variables-and-context/) for secrets and [Test.md](/docs/kane-cli-testmd/) for the file format.

## Card checkout

Card checkout is the path most payment changes touch. These recipes cover the happy path, a declined card, a stored card, and a guest card, and each one checks the receipt rather than only the success banner.

### Hosted checkout session

A hosted checkout page has to charge the amount the order summary shows. This recipe checks the plan and total, pays with a test card, and then checks the receipt for the payment ID, the amount paid, the card, and the succeeded status.

```markdown hosted-checkout-session_test.md
---
mode: testing
url: https://your-app.example.com/checkout
max_steps: 40
tags: [payments, checkout]
---

# Hosted checkout

## Verify the checkout total
Verify the order summary shows "Pro plan — annual" at "$240.00" and "Total due" of "$240.00".

## Fill in the card
Type "4242 4242 4242 4242" into "Card number", "12 / 34" into "Expiry", "123" into "CVC", and verify the pay button reads "Pay $240.00".

## Pay
Click "Pay $240.00" and verify a green banner titled "Payment successful" appears.

## Verify the receipt
Verify the receipt shows "Payment ID" of "pi_3Qb101Mx03", "Amount paid" of "$240.00", "Card" of "Visa ••••4242" and "Status" of "succeeded".
```

Kane CLI compares the receipt with the order summary, so a success banner over a different amount or a failed status fails the run.

```markdown declined-card-recovery_test.md
# Declined card recovery

## Attempt with the declining card
```

Wallets, bank redirects, and local methods add a popup, a second site, or a validation step to checkout. These recipes follow the shopper through that extra step and back.

```markdown webhook-status-parity_test.md
# Webhook status parity

## Take a payment
Choose "Card", type "4111 1111 1111 1111" into "Card number", "03 / 30" into "Expiry", "737" into "CVC", and click "Pay €129.50".

## Verify the shopper result
Verify a green banner titled "Payment authorised" shows "Result code" of "Authorised" and "PSP reference" of "PSP883000001717".

## Open the merchant order page
Click "View the merchant order page" and verify "Order reference" reads "ORD-55120", "Status shown to merchant" reads "Authorised" and "PSP reference" reads "PSP883000001717".

## Verify the notification agrees
Verify the webhook list shows "AUTHORISATION · ORD-55120" with "success: true", and the parity card reads "UI status" of "Authorised", "Notification status" of "Authorised" and a badge saying "UI status matches the notification".
```

Kane CLI checks the PSP reference on both pages and the parity card that compares them, so an order page that drifts from the notification fails the run.
